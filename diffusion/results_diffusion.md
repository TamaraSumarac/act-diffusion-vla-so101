## Deployment note: inference latency and the DDIM-10 checkpoint variant

**Problem.** Off-robot smoke test — loading the checkpoint and timing `predict_action_chunk` on a recorded observation (no robot involved) measured **9.2 s per chunk** on the deployment machine (Apple M1 Mac, mps). A chunk of 32 actions covers only 32/30 ≈ 1.07 s of robot time at 30 Hz, so the arm would move for ~1 s and then freeze for ~8 s while the next chunk computes — this is undeployable. The cause is architectural: Diffusion Policy generates a chunk by starting from noise and iteratively denoising it with the U-Net. The training preset uses DDPM with `num_train_timesteps=100`, and with `num_inference_steps=None` the sampler retraces the full 100-step training schedule — 100 U-Net forward passes at ~65 ms each (263M params on mps) ≈ 6.5 s of the total.

**Fix (the paper's own recipe).** Diffusion Policy ([Chi et al., 2023](https://arxiv.org/abs/2303.04137), §3.4) prescribes training with DDPM (Denoising Diffusion Probabilistic Models) and sampling at deployment with DDIM (Denoising Diffusion Implicit Models; [Song et al., 2021](https://arxiv.org/abs/2010.02502)), which decouples training and inference step counts — in their setup, 100 train / 10 inference steps at 0.1 s latency on an RTX 3080. Since DDIM shares DDPM's training objective, this is an inference side swap on the already trained checkpoint — no retraining.

**How was the fix achieved.** In LeRobot 0.6.1, scheduler settings can't be changed at runtime — both post-load config mutation and `from_pretrained` kwargs leave the `DDPMScheduler` in place, silently (verify with `type(policy.diffusion.noise_scheduler).__name__`). The only path that reaches scheduler construction is the checkpoint's `config.json` itself, so the checkpoint was copied to `checkpoints_diffusion_baseline/100000_ddim10/` with two fields changed: `"noise_scheduler_type": "DDIM"`, `"num_inference_steps": 10`. Original file stayed untouched; the folder name says what's in it, so there's no need to open `config.json` to check which scheduler a given eval ran.

**Result.** Load time check confirmed `DDIMScheduler` with 10 steps; inference dropped **9.2 s → 861 ms** per 32-action chunk (10.7×). In synchronous deployment arm pauses ~0.9 s per chunk instead of ~9 s — but that takes the duty cycle from undeployable to workable. Action accuracy check: each diffusion call starts from freshly sampled noise, so even repeat runs of the *same* sampler differ by 1–2° per joint (unlike ACT, where identical input gives identical output). DDIM-10's predictions on a training frame landed inside that same range relative to DDPM — the speedup cost nothing measurable.
